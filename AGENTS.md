## CodeGraph

In repositories indexed by CodeGraph (a `.codegraph/` directory exists at the repo root), reach for it BEFORE grep/find or reading files when you need to understand or locate code:

- **MCP tool** (when available): `codegraph_explore` answers most code questions in one call — the relevant symbols' verbatim source plus the call paths between them, including dynamic-dispatch hops grep can't follow. Name a file or symbol in the query to read its current line-numbered source. If it's listed but deferred, load it by name via tool search.
- **Shell** (always works): `codegraph explore "<symbol names or question>"` prints the same output.

If there is no `.codegraph/` directory, skip CodeGraph entirely — indexing is the user's decision.

### Практичне використання CodeGraph у цьому проєкті

- На старті задачі перевіряти `codegraph status`. Якщо індекс свіжий, першим
  запитом для розуміння коду використовувати `codegraph explore` з назвою
  функції, файла або потоку поведінки. Виведений CodeGraph вихід вважати вже
  прочитаним і не дублювати його `grep`/`sed`/повторним читанням.
- Для широкої, незрозумілої або міжмодульної задачі спочатку використовувати
  `codegraph context "опис задачі" --max-nodes 12`; потім уточнювати лише
  потрібні символи через один-два `explore`. Для автоматизації, де важлива
  компактність і стабільний парсинг, використовувати `--format json`.
- Для малої задачі обмежувати `explore` параметром `--max-files 3-5` і робити
  один точний запит. Не будувати великий контекст проєкту без потреби.
- Перед зміною shared-функції, сховища, API, маршруту або компонента спочатку
  використовувати `codegraph impact "SymbolName" --depth 2`; для вузького
  потоку — `callers`/`callees`. Це визначає реальний blast radius до редагування.
- Після змін спочатку перевіряти `codegraph status`. Покладатися на авто-sync;
  запускати `codegraph sync` лише якщо статус показує pending/stale або коли
  індекс потрібен у скрипті. Повний `codegraph index` не запускати після
  звичайної правки.
- Для підбору тестів використовувати
  `git diff --name-only | codegraph affected --stdin --quiet`. Результат є
  мінімальним набором для цільової перевірки, але не замінює lint, typecheck,
  build чи обов'язкові project-specific smoke-тести.
- Для структури індексованого коду використовувати `codegraph files`, а для
  точного джерела одного символу — `codegraph node`. `query` — правильна назва
  CLI-команди пошуку; не використовувати помилкове `codegraph seach` або
  припускати наявність окремої CLI-команди `search`.
- CodeGraph не є заміною пошуку тексту в Markdown, JSON, CSS, зображеннях,
  логах або згенерованих артефактах. Для них і для перевірки точного тексту
  використовувати звичайні інструменти лише після перевірки межі CodeGraph.
- Якщо CodeGraph показує staleness banner для щойно зміненого файла, не
  робити висновок зі старого джерела: перечитати тільки цей конкретний файл
  напряму й після стабілізації індексу повторити вузький запит.
- Не повторювати однакові `explore`/`node` запити й не запускати `codegraph ui`
  для звичайної правки. UI використовувати лише коли потрібен візуальний
  розбір архітектури або його прямо попросив власник.
- Для іншого репозиторію передавати шлях через `codegraph -p PATH` або
  `projectPath` MCP, але не ініціалізувати індекс у сторонньому проєкті без
  прямої потреби. Не видаляти `.codegraph/` і не ділити один індекс між
  різними ОС.

### Діагностика production build

- Стандартна команда проєкту — `npm run build` (Next.js Turbopack). Не
  додавати `--webpack` у скрипти або документацію як постійний обхідний шлях:
  його дозволено запускати лише як контрольний тест, щоб відокремити проблему
  Turbopack від проблеми середовища.
- Відсутність нового рядка в терміналі перші 1-2 хвилини не доводить зависання.
  Для першої production-збірки дати до 5 хвилин у звичайному локальному
  Terminal, періодично перевіряючи, чи є прогрес або помилка.
- Помилки `EPERM` під час запису/очищення `.next` або `out/` у Codex sandbox
  означають обмеження середовища перевірки, а не помилку Next.js чи сайту.
  Повторити build після надання доступу до build-артефактів або в локальному
  Terminal, і лише тоді робити технічний висновок.
- Попередження Node на кшталт `DEP0205` не є доказом несумісності. GitHub
  збирає проєкт на Node 22; для відтворюваності локально використовувати Node
  22 LTS. Не оголошувати Node 26 причиною проблеми без відтворення на Node 22
  та без конкретного stack trace.
- Перед релізом звіряти `package.json` і тег `v<version>`: версію підвищувати
  до push у `main`, а наявний release-тег ніколи не намагатися перевикористати
  для іншого коміту.

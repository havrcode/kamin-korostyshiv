# Правила роботи над «Камінь Коростишів»

1. Мова інтерфейсу й документації для власника — українська.
2. Не змінювати візуальну систему без конкретної причини: шрифти, кольори,
   відступи й композицію перевіряти окремо на телефоні та комп’ютері.
3. `v0.1.0` — незмінна базова версія й точка відкату; цей тег ніколи не
   пересувати й не перевикористовувати для нового коміту.
4. Власник дозволив для цього одноосібного проєкту автоматичний робочий цикл:
   перевірки → публічний Sites → fast-forward оновлення приватного GitHub
   `main`. Для ризикових або великих змін Codex може обрати окрему гілку/PR.
   Кожну завершену й перевірену версію одразу позначати новим незмінним
   release-тегом без окремого підтвердження власника.
5. Контактні та брендові дані зберігати централізовано в `app/site-config.ts`.
6. Дані каталогу не дублювати в JSX; використовувати `app/data/catalog.ts`.
7. Не показувати користувачу фальшиве підтвердження надсилання заявки.
8. Реальна заявка має спочатку надійно зберігатися в D1, а сповіщення
   Telegram — створюватися в outbox у тій самій транзакції.
9. Закупівельні ціни, націнки, секрети й приватні файли ніколи не передавати
   до публічного JavaScript і не зберігати в репозиторії.
10. Для анімацій завжди поважати `prefers-reduced-motion`; контент має бути
    доступним і без JavaScript.
11. Після зміни UI виконати lint, typecheck, test/build і візуальну перевірку
    щонайменше у вузькому та широкому viewport.
12. Після суттєвої зміни оновлювати `CHANGELOG.md`,
    `docs/PROJECT_STATUS_UA.md`, `docs/HANDOFF_UA.md` і відповідний розділ
    архітектури, якщо змінюється поведінка, структура або інфраструктура.
13. Публічний frontend збирається як статичний Next.js export у `out/`.
    Не повертати Vinext/Vite або виконання публічних сторінок через Worker без
    нового зафіксованого архітектурного рішення. Worker призначений для API,
    захищеної адмінської логіки, D1/R2 та фонових задач.
14. Перед кожним завершеним оновленням підняти версію в `package.json`.
    `.github/workflows/release-tag.yml` після push у `main` повторно виконує
    `npm ci`, lint, typecheck і тести, а потім створює тег
    `v<package.version>`. Не пересувати наявні теги й не вимикати перевірки.
15. Канонічна історія розробки — приватний GitHub `main` разом із незмінними
    тегами. Хмарне середовище не може фізично оновити папку на Mac; локальний
    Codex перед роботою виконує `git fetch origin --prune --tags`, перевіряє
    незбережені зміни й лише тоді робить `git pull --ff-only origin main`.
16. Worker API заявки має відмовляти без налаштованих D1 і rate-limit binding.
    Публічну форму не підключати до API до погодження тексту згоди, строку
    зберігання персональних даних і одержувачів Telegram.
17. Telegram-процесор не має claim-ити outbox без D1, bot token і chat ID.
    Тимчасові помилки повертаються в `PENDING`, `FAILED` є остаточним станом,
    а завершення події завжди перевіряє той самий `locked_at` lease.
18. Згенеровані зображення завжди прямо позначати як візуалізації, не називати
    їх фотографіями виконаних робіт і замінювати по одному без зміни стабільних
    `id`/`slug`, коли власник надасть реальні матеріали.
19. До активації власного Cloudflare, D1, Turnstile, Access і погодження
    юридичних даних Sites лишається повною публічною демонстрацією, але не
    збирає персональні дані й не видається за активний production бізнесу.
20. Для малих задач Codex читає `AGENTS.md`, `docs/BRIEF_UA.md` і тільки
    потрібні файли коду/документації. `docs/HANDOFF_UA.md`,
    `docs/DECISIONS_UA.md` та весь `docs/` перечитувати лише для великих,
    ризикових або архітектурних змін.
21. Для щоденної UI-перевірки перевага за локальним preview. Якщо потрібен
    hot reload, запускай `npm run dev`; якщо треба економно переглянути вже
    зібраний сайт, запускай `npm run build`, потім `npm run preview:static`.
    ChatGPT Sites публікувати після успішних перевірок як релізний/demo-крок,
    а не використовувати як заміну локальному серверу на кожній дрібній правці.

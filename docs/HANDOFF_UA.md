## 6. Обрана архітектура

Основний напрямок — один Cloudflare-проєкт, спочатку на Free-плані:

- React + TypeScript — клієнтський інтерфейс;
- Next.js App Router зі статичним `output: "export"` — структура та збірка;
- готові файли в `out/` — максимально кешований публічний frontend;
- Cloudflare Worker — `/api/*`, Access-перевірка адмінки й приватна серверна логіка;
- D1 — заявки, outbox і audit; статичний демо-каталог поки живе в TypeScript;
- R2 — фото товарів і майбутні приватні фото клієнтів;
- Cron Triggers — повторні спроби Telegram та очищення чернеток;
- Cloudflare DNS/CDN/TLS/WAF — домен, доставка й базовий захист.

Постійний Node.js-процес не потрібний. PHP + MySQL залишається можливим
резервним шляхом, але не є поточним рішенням. Варіант із двома окремими
платними хостингами відкладено як зайво складний і потенційно дорожчий.

ChatGPT Sites зараз використовується для публічного preview і релізної
перевірки. Власний Cloudflare-акаунт і production-домен підключатимуться
окремим етапом.

Vinext, Vite, Cloudflare Vite plugin і шаблонний Worker-рендеринг прибрані
31 серпня 2026 року. Це не змінює вигляд сайту й не скасовує Cloudflare:
окремий Worker відповідає лише за `/api/*`, D1/R2, Telegram і
захищені адмінські операції.

## 8. Виправлений дефект блоку переваг

Блок «Точний проєкт / Виготовлення / Зручне замовлення» був центрований через
`left: 50%` і `transform: translateX(-50%)`. Той самий `transform` використовує
scroll-reveal-анімація для `translateY`. Після появи клас `is-visible`
перезаписував горизонтальний transform, тому блок починався від середини
екрана й з’їжджав вправо на ПК та телефоні.

Рішення: центрування через `inset-inline: 0` і `margin-inline: auto`. Тепер
анімація володіє `transform`, а layout — горизонтальним центруванням. Додано
регресійний тест, який не дозволяє повернути `translateX` у це правило.

## 9. Реальні заявки й Telegram

Код реальної форми готовий у `v1.0.0`, але на Sites навмисно вимкнений до
власних bindings і юридичного погодження. Сервер не довіряє frontend і
повторно перевіряє всі поля. Погоджений надійний потік:

1. `POST /api/v1/leads` приймає й нормалізує дані.
2. В одній D1-транзакції створюються заявка та outbox-подія `PENDING`.
3. Клієнт отримує успіх тільки після збереження заявки й публічний номер.
4. Worker одразу пробує відправити Telegram через `ctx.waitUntil`.
5. Збій Telegram не видаляє заявку.
6. Cron повторює лише готові `PENDING` або застарілі `PROCESSING` події з
   атомарним claim; остаточний `FAILED` автоматично не надсилається.
7. Остаточний `FAILED` видимий адміністратору.

Можливий дубль Telegram після невизначеної мережевої відповіді не можна
математично виключити, тому повідомлення міститиме унікальний номер заявки.

- Секрети Cloudflare/Telegram, закупівельні ціни, формули націнки, приватні

- Фото клієнтів — приватний R2, короткі signed URL, строк зберігання й видалення.

## 11. Каталог

- Категорії й товари мають незмінні внутрішні `id` та окремі `slug` для URL.
- Людську назву можна змінювати без руйнування старих заявок.
- Публічні маршрути: `/catalog`, `/catalog/[categorySlug]` і
  `/catalog/[categorySlug]/[productSlug]`; приховані записи не потрапляють у
  static params або sitemap.
- Картка: візуалізація або згодом реальне фото, людська назва на кшталт
  «Стіл з лавкою № 1», «Лампадка № 6», «Підвіконня заокруглене», матеріал,
  короткий опис, режим ціни й CTA консультації.
- Вибір передає `categoryId` і `productId`; заявка додатково зберігає snapshot
  назви й публічної ціни.
- Прихований товар залишається в історичних заявках.
- Якщо БД недоступна, не показувати вигадану fallback-ціну; чесно писати
  «Вартість уточнюється».

Поточний публічний набір у `1.1.4`: столи та лавки, лампадки, вази, інший
декор, камінь для дому. Пам’ятники приховані публічно, але їх можна повернути
зміною `published` після погодження.

## 12. Кошториси

- `internalCost`: закупівля, матеріал, робота, відходи й сторонні послуги.
- `customerPrice`: внутрішня собівартість плюс серверні правила націнки,
  доставки, монтажу, мінімальної маржі та округлення.
- Клієнт бачить тільки дозволений результат: орієнтир, діапазон, «від» або
  «після перевірки майстром».
- Кожен кошторис зберігає snapshot компонентів і цін, версію правил, ручну
  поправку, автора перевірки та строк дії.
- Зміна поточних цін не переписує старі пропозиції.

## 13. 2D/3D-конструктор

Стратегічна цінність сформульована так:

> зрозумілий ескіз → правильний склад виробу → перевірений кошторис.

Перший запуск сайту не чекає конструктора. Після запуску:

1. узгодити 5–10 реальних типових замовлень і правила виробництва;
2. зробити 2D-конфігуратор перевірених пресетів;
3. додати 1–3 портретні зони, камінь по елементах, front/back і JSON;
4. додати crop фото, кольорову вставку й гравійований grainy grayscale preview;
5. додати server pricing і ручну перевірку;
6. лише потім — оптимізовані 3D-моделі найпопулярніших пресетів із 2D fallback.

Спочатку це конкурентна перевага власного сайту. Ядро правил проєктується
незалежно, щоб пізніше можна було вирішити: залишити ексклюзивним, ліцензувати
white-label або створити embeddable SaaS. SaaS не будувати до доказу цінності.

Повна специфікація: `docs/CONSTRUCTOR_2D_3D_PLAN_UA.md`.

## 14. Робочий цикл Codex, GitHub і Sites

Власник дозволив для погоджених змін автоматичний цикл:

1. Codex читає `AGENTS.md` і документацію.
2. Працює з локальною копією проєкту.
3. Виконує lint, typecheck, production build, tests і потрібну UI-перевірку.
4. Створює зрозумілий commit.
5. Публікує перевірений стан на публічному Sites.
6. Fast-forward оновлює приватний GitHub `main`.
7. GitHub Actions повторно перевіряє коміт і створює незмінний release-тег.
8. Codex перевіряє, що тег вказує саме на опублікований commit.
9. Оновлює `PROJECT_STATUS_UA.md`, цей handoff і `CHANGELOG.md`.

Для малих задач достатньо читати `AGENTS.md`, `docs/BRIEF_UA.md` і цільові
файли. `README.md`, повний handoff і журнал рішень відкривати, коли зміна
зачіпає архітектуру, релізний процес, безпеку, каталог як модель даних або
важливі бізнес-рішення. Повний `npm test`, browser/CDP, screenshots,
image generation і Sites-публікації не запускати для дрібних правок без прямої
потреби.

Для великої/ризикової зміни дозволено feature-гілку й Draft PR. Не виконувати
одночасні незалежні правки в одній гілці. На Mac перед роботою виконувати
`git fetch origin --prune --tags`, перевіряти `git status -sb`, а потім робити
`git pull --ff-only origin main`.

Важливо: поточне хмарне середовище не записує файли безпосередньо на Mac.
Локальна папка оновлюється через `git pull` або коли проєкт відкрито саме в
локальному Codex desktop. GitHub є мостом і резервною синхронізованою копією.

## 17. Публікація Sites і локальний image pipeline

Перевірений сценарій останньої успішної публікації збережено в
`docs/SITES_PUBLISH_UA.md`. Скрипт `scripts/prepare-sites-release.sh` повторює
його безпечну частину: тимчасовий клон внутрішнього Sites Git, `HTTP/1.1`,
`postBuffer=500 MB`, `maxRequestBuffer=100 MB`, виключення локальних каталогів,
перевірка однакового Git tree, fast-forward push і package archive. Save/deploy
виконуються через Sites connector, бо credential і deployment API не повинні
потрапляти в репозиторій.

Окремий `scripts/prepare-product-image.mjs` готує фото з телефона у WebP.
Канонічний кадр сайту — `3:2`, рекомендована ширина — до 1536 px, quality —
86. Оригінал не перезаписується.

Production-контур адмінки фото вже підготовлено: максимум п’ять активних фото
на товар, R2 для оригіналів і WebP, D1 для порядку/видимості/soft-delete,
Images binding, Access/JWT і server-side ліміт. Потрібно створити R2 buckets,
додати власний media custom domain і застосувати міграцію. Окремий піддомен або
універсальний SaaS для самої адмінки не створювати; нейтральний CLI можна
винести у приватний пакет після другого реального проєкту.

Окремо додано контур клієнтських вкладень: R2 bucket `LEAD_ATTACHMENTS` має
бути приватним, а D1-міграція `0004_bumpy_blink.sql` застосована до Worker.

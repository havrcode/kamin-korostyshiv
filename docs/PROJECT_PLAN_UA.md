# План розробки «Камінь Коростишів»

## 1. Мета продукту

Сайт має не просто показувати красиві фотографії. Він повинен провести людину
від першого інтересу до зрозумілої, не загубленої заявки на прорахунок:

1. людина знаходить потрібну категорію;
2. переглядає реальні вироби з людськими назвами;
3. обирає конкретний товар або позначає кілька варіантів;
4. переходить до форми, де категорія й товар уже підставлені;
5. залишає контакт і побажання;
6. сервер надійно зберігає заявку;
7. майстер бачить її в адмінці й отримує Telegram-сповіщення;
8. після розмови формується перевірений кошторис.

## 2. Архітектурний напрямок

Ціль — один Cloudflare-проєкт без двох платних серверів:

- React + TypeScript: сторінки, каталог, форма, адмінський інтерфейс;
- статичні файли Cloudflare: HTML, JavaScript, CSS, оптимізовані зображення;
- Cloudflare Worker: API та захищена серверна логіка;
- D1: заявки, товари, ціни, статуси, outbox, аудит;
- R2: оригінали й похідні зображення, майбутні фото клієнтів;
- Cron Triggers: повторні спроби Telegram і технічне обслуговування;
- Cloudflare DNS/CDN/WAF: домен, кеш, TLS та базовий захист.

Поточний Sites залишається середовищем демонстрації. Власний Cloudflare стане
джерелом production-інфраструктури після підключення акаунта.

## 3. Версії

### v0.1.0 — збережена основа

- початкова візуальна концепція;
- адаптивна односторінкова структура;
- локальна історія й тег збережені окремо.

### v0.1.1 — контакт і підтримувана frontend-основа

- номер телефону в єдиному конфігу;
- справжні `tel:`-посилання;
- виправлений мобільний заголовок;
- категорії й довідкові дані в окремому модулі;
- передавання вибраної категорії у форму;
- чесний стан попередньої форми;
- делікатні scroll-reveal-анімації з підтримкою reduced motion;
- документація, правила й автоматичні перевірки.

Критерій готовності: телефон працює; слово не обрізається на типовому вузькому
екрані; вибрана категорія з’являється у формі; lint/typecheck/test успішні.

### v0.1.2 — статична production-основа

- прибрати Vinext/Vite й виконання публічної сторінки через Worker;
- залишити React + TypeScript і Next.js App Router;
- генерувати звичайні статичні HTML/CSS/JavaScript-файли в `out/`;
- залишити майбутньому Worker тільки `/api/*`, захищені операції `/admin`, D1,
  R2, Telegram і фонові задачі;
- зберегти дизайн, поведінку, SEO та доступний початковий HTML;
- додати тест, який не дозволяє випадково повернути Vinext у залежності.

Критерій готовності: `npm run build` створює `out/index.html`, у залежностях і
lock-файлі немає Vinext/Vite/Cloudflare Vite plugin, а Sites віддає ту саму
сторінку як статичний сайт.

### v0.1.3 — безпечна основа заявки

- типізований серверний контракт заявки без довіри до браузера;
- нормалізація українського номера до формату `+380XXXXXXXXX`;
- перевірка імені, категорії, повідомлення, згоди та honeypot-поля;
- D1-схема `leads` і `notification_outbox`;
- унікальні публічний номер заявки та ключ ідемпотентності;
- індекс для безпечного пакетного захоплення outbox-подій;
- перша незмінна Drizzle-міграція й unit-тести;
- GitHub Actions, який повторно перевіряє `main` і автоматично створює
  незмінний тег `v<package.version>`.

На цьому етапі публічна форма ще не надсилає персональні дані: D1 binding та
API вмикаються тільки після узгодження тексту згоди, строку зберігання й
одержувачів сповіщень.

### v0.1.4 — перевірений Worker API-контур

- окремий Worker entrypoint тільки для `/api/*`, без рендерингу сторінок;
- `POST /api/v1/leads` із JSON content type та межею 16 КіБ;
- обов’язковий `Idempotency-Key` і повтор із тим самим номером заявки;
- Cloudflare rate-limit binding із відмовою, якщо він не налаштований;
- один атомарний D1 batch для `lead + notification_outbox`;
- обробка одночасних однакових запитів і рідкісної колізії публічного номера;
- безпечні API-відповіді та логи без персональних даних;
- unit-тести HTTP, репозиторію, rate limit, повторів і dry-run збірка Worker.

Критерій готовності: API-код компілюється для Cloudflare Worker, усі тести
проходять, а без D1/rate-limit binding повертається `503` і нічого не
зберігається. Публічна форма все ще не викликає endpoint.

### v0.3.0 — реальний каталог

- сторінка `/catalog`;
- маршрут `/catalog/[categorySlug]`;
- маршрут `/catalog/[categorySlug]/[productSlug]`;
- реальні категорії, товари, людські назви й фото;
- стабільні `id`/`slug`, які не залежать від назви;
- одиночний вибір «Мене цікавить цей виріб»;
- за потреби список із кількох позначених виробів;
- передавання `categoryId`, `productId` і назви у форму та заявку;
- базове керування товарами через адмінку;
- SEO-заголовки й Open Graph для кожного товару.

Картка товару спочатку не повинна прикидатися інтернет-магазином. Достатньо:
фото, людська назва (`Підвіконня заокруглене` або `Підвіконня №1`), матеріал,
короткі особливості, режим ціни й кнопка консультації.

## 4. Каталог: правила, які не доведеться ламати

- Категорія й товар мають внутрішній незмінний `id`.
- `slug` використовується в URL; людську назву можна редагувати.
- Вибір товару зберігає `productId`, а не лише текст назви.
- Заявка додатково зберігає snapshot назви й публічної ціни на момент надсилання.
- Прихований товар не зникає зі старих заявок.
- В адмінці можна змінювати порядок, видимість і режим ціни.
- Неіснуючий/прихований товар сервер відхиляє або позначає для ручної перевірки.

## 5. Анімації

Додаємо тільки анімації, які підтримують ієрархію сторінки:

- м’яка поява секції з невеликим рухом угору;
- незначна послідовність карток;
- уже наявне акуратне збільшення фото при hover;
- плавне відкриття мобільного меню.

Не додаємо:

- примусове перехоплення прокручування;
- довгі заставки;
- паралакс, що погіршує читання;
- анімації, без яких контент зникає;
- ефекти, що ігнорують `prefers-reduced-motion`.

## 6. Правила Git

1. Спочатку зміни й локальна перевірка.
2. Для невеликих погоджених змін цього одноосібного проєкту дозволено прямий
   fast-forward commit у `main` після чистих перевірок.
3. Значні, ризикові або експериментальні зміни виконуються в окремій гілці;
   за потреби створюється Draft PR.
4. Після перевірок актуальний стан публікується на Sites для тестування.
5. Тег `v0.1.0` ніколи не пересувати.
6. Кожну завершену й перевірену версію одразу автоматично тегувати як
   `v<package.version>` без окремого підтвердження; наявні теги не пересувати.
7. Після кожного завершеного блоку оновлювати статус, handoff і changelog.
